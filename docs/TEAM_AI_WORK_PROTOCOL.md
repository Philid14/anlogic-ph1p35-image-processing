协议版本：`TEAM_PROTOCOL_V1`。制定日期：2026-10-14。

本文件供三名队员及其各自的 AI 共同使用。先读仓库根目录 `AGENTS.md`，再读本文件，再读负责人为当前任务确认的 Issue 和接口说明。赛题要求以原始 PDF 第 16–18 页为准；本协议补充分工与协作方式，不替代赛题基准和实验追溯要求。

## 2. 三人的任务分工

| 角色 | 开发内容 | 赛题对应 | 必须交付 |
|---|---|---|---|
| MAIN：负责人及其 AI | 原图显示、多算法切换、边缘提取与区域填充、图像质量自动调节；主线性能与资源优化；系统集成 | 基础项、扩展一/四、进阶一/五 | 主线 RTL、完整构建、归档 bit、真实上板记录、版本决策 |
| TARGET：队友一及其 AI | 指定颜色目标检测、动态定位、包围框/中心标记/坐标标注 | 扩展二、进阶二 | 独立检测和标注模块、模型/自检、接口说明、资源与延迟说明、演示步骤 |
| LATENCY：队友二及其 AI | 帧身份相关统计、采集/显示帧率、同帧延迟测量、性能信息可视化 | 进阶三；为扩展四提供测量依据 | 独立统计/计时/显示模块、模型/自检、测量口径、精度与异常说明、演示步骤 |

### 2.1 MAIN 的核心工作

1. 收口现有 candidate 的上板验收，形成稳定且可回退的主线基线。
2. 完成原图与多种算法的统一切换和状态显示。
3. 开发边缘提取与区域填充，保留可说明的数据流和流水线结构。
4. 探索自动曝光、白平衡或其他图像质量调节；每个实验只改变一个主要因素，不一次混改曝光、AWB、Gamma、CCM 等独立因素。
5. 根据真实构建与测量结果优化资源和延迟；进阶三的“测量与可视化”不等于已经完成延迟优化。
6. 为两位队友提供规范化接口，连接模块，统一 OSD 和模式控制，完成整机验收。

MAIN 统一维护：主工程全部接线、实际编译的 ISP、sensor 寄存器/I²C、MIPI、DDR、HDMI、时钟复位、约束、TD 入口/IP 配置、共享字库、整体实验记录与正式 bit 归档。

### 2.2 TARGET 的分阶段工作

- T1：在单个主要颜色目标、背景较易区分的场景下，完成参数化颜色分类；首个演示目标默认红色。阈值在模块内部参数或确认后的配置接口中表达，不修改主线 AWB/曝光来迁就检测。
- T2：统计匹配像素数、包围框及包围框中心，每个完整帧输出一次结果，附帧身份和有效状态。包围框中心不是像素质心，报告要准确区分。
- T3：开发独立标注模块，输出框线、中心十字和坐标的覆盖请求；由 MAIN 合成至对应显示帧。
- T4：完成目标移动、目标消失与重现时的状态更新和适度防抖，支持可重复的动态跟踪演示。

第一版不做神经网络、不增加整帧缓存、不声称支持多物体独立识别。若多个同色区域被统计成一个框，必须报告这个限制；独立目标计数、连通域和形状识别属于另一个任务，不能暗中扩大范围。

### 2.3 LATENCY 的分阶段工作

- L1：完成采集帧计数、显示事件计数及帧率统计，明确 HDMI 输出刷新率与独立图像帧率的区别。
- L2：在模拟事件输入下完成帧身份匹配、计时和异常处理，证明模块本身可独立工作。
- L3：由 MAIN 接入实际采集、缓存和显示事件后，完成同一帧的延迟测量。
- L4：提供帧号、有效延迟、最近/最小/最大延迟及状态信息的独立覆盖模块，供 MAIN 接入统一 OSD。

本项目的测量口径是“FPGA 内 MIPI 解码后某帧首个有效像素 → 该帧首个有效像素实际送至 HDMI 输出”。不包含 sensor 曝光等待、镜头到光电转换时间或显示器内部延迟。两个独立帧计数器相减或两个 VSYNC 间隔不能替代同帧延迟。

延迟主统计默认针对完整有效帧的首次显示。重复显示同一帧单独标记，可报告图像年龄，但不冒充新帧或重复计入首次显示延迟统计。暂未接入硬件身份关联时，只能称“独立模块完成”或“模拟事件验证通过”，不能称“进阶三已整机完成”。

## 4. 三人之间的技术接口协议

### 4.1 状态与版本

- 本节是待 MAIN 落成适配器的共同边界，不能假设主线已经提供这些端口。目前主线没有可直接交付的统一采集/显示帧身份接口。
- 每个功能维护 `INTERFACE.md`，使用 `接口草案 → 负责人确认 → 已实现 → 已接入` 的状态；注明协议版本、主线基线 SHA、信号方向/位宽、时钟复位、单位、延迟、失效条件。
- 下述规范化语义为 V1 默认值。实际 HDL 端口表由功能作者提交，MAIN 确认后冻结；确认前可开发模型和独立模块，但不能自行推断主线接线。
- 结果由 `{session_id, frame_id}` 识别：两者均为 32 位；复位/重新采集开始新 session；帧号回绕前开启新 session，清除旧关联。缓存槽号不能单独当成帧身份。

### 4.2 MAIN → TARGET：规范化像素观察流

- 默认 1280×720、RGB888、4 像素/拍、96 位。在规范化接口中 lane0=`[95:72]`、lane1=`[71:48]`、lane2=`[47:24]`、lane3=`[23:0]`，按显示坐标从左到右排列；MAIN 验证实际主线映射，必要时由适配器转换。
- 原点为画面左上角，x 向右、y 向下。提供该拍 lane0 的 `x0[10:0]` 与 `y[9:0]`，其他 lane 的 x 为 x0+1/+2/+3。
- `pixel_valid` 为 1 时消费整拍四个像素，不向采集链路施加反压。默认宽度可被 4 整除；格式或宽度变化按接口变更流程处理。
- `sof/eol/eof` 分别伴随本帧首个、本行最后、本帧最后一个有效拍；session/frame 身份整帧稳定。中断/错误帧另给出 `frame_abort`，检测模块丢弃该帧结果。
- 主线现有提前帧通知不等于上述 `sof`。MAIN 必须转换和对齐，队友不能把任意 `tuser` 直接解释为首个有效像素。
- 观察点取可用于颜色判断的彩色流，位于边缘/区域填充等风格化输出之前。颜色校正变化可能影响阈值，即使端口不变也要通知 TARGET 重新评估。

### 4.3 TARGET → MAIN：检测结果及标注

- 完整帧结果包含：session/frame 身份、结果有效、目标存在、颜色类别、匹配像素数、xmin/xmax/ymin/ymax、包围框中心坐标；坐标仍对应原图的 1280×720 范围，不能使用当前 Sobel 的 640 点水平采样坐标代替。
- x/中心 x 为 11 位，y/中心 y 为 10 位，像素数量为 20 位；包围框两端均包含在范围内。无目标时目标存在为 0，坐标清零。最后一个有效拍的四个像素必须纳入结果。
- 结果在完成后原子发布并保持稳定供接收。跨时钟域由经确认的握手/FIFO 适配完成，不能直接采样多个异步坐标位。
- 检测结果在帧末才可用。MAIN 将其与对应缓存帧关联，在读出时使用匹配结果；不能把上一帧的框悄悄标成当前帧检测结果。
- 标注模块接受 MAIN 提供的显示坐标、有效像素和整帧锁存的结果，输出 `overlay_valid` 与 RGB888 覆盖颜色，帧/行内不改变基础像素数量。

### 4.4 MAIN ↔ LATENCY：事件和缓存帧身份

- MAIN 提供采集开始、帧有效完成/中断、读出所选帧身份及 HDMI 实际首有效像素事件。事件具有 session/frame 身份；四个缓存地址区只是当前实现细节，不是永久接口常量。
- 对缓存区的身份及时间元数据按写入代次管理，错误帧回退、覆盖和读出预取均要保留正确对应。读者选择帧时需锁存对应元数据，并随像素路径带到实际输出，不能在输出时读取已被覆盖槽位的“最新身份”。
- LATENCY 采用共同参考时基，提供时间计数、事件匹配和统计。参考频率必须来自核实的时钟配置，以参数输入，不把名义频率当作精确实测频率。
- MAIN 和 LATENCY 在 `INTERFACE.md` 中明确事件 CDC 由谁实现、时间戳形成位置、采样分辨率与误差边界。事件及身份应原子传递；不能直接跨域采样正在变化的宽时间计数器。
- 未匹配、帧中断、元数据覆盖、事件丢失/队列满和复位均输出无效原因；无效样本不计入延迟统计。统计不得反向阻塞采集/显示，也不能依靠丢事件来宣称吞吐达标。
- 缓存策略变化由 MAIN 更新适配层；保持身份/事件契约后计时模块可复用。算法延迟改变时数值应如实变化；时钟、格式或帧关联变化后必须重新验证，不能承诺后续完全不受影响。

### 4.5 共用 OSD 与资源边界

- MAIN 分配各功能显示区域，统一字体、位置和合成顺序；默认优先级为原“安路”Logo/主线状态 > 性能文字 > 目标框/十字 > 基础图像。不能遮挡 Logo 或改写已有字库。
- 两位队友交付参数化覆盖模块，不自行绑定按键/引脚、改变主线模式或私自添加 UART。
- 第一版 TARGET 使用流式统计，LATENCY 使用少量元数据与计数器；均不新增整帧缓存或改用其他 FPGA 厂商 IP。
- 提供自检、模块资源估计/实际结果、最大工作频率依据和流水延迟，MAIN 决定整机预算。当前控制版资源/时序只是一条历史基线，不能当作扩展后的结果。

## 5. GitHub 工作协议（必须执行）

### 5.1 一个仓库，各自分支

- 三人各自 clone 同一仓库；本地根路径可以不同，使用相对路径，不写死负责人的 D 盘路径。
- 不为功能单独建立独立 Git 仓库，不共用一个可同时修改的工作目录。多个 AI 使用同一电脑时使用独立 checkout/worktree，并分别绑定任务。
- 分支规则：`codex/main/<任务>`、`codex/target/<任务>`、`codex/latency/<任务>`。一个分支处理一个 Issue 的主要任务。
- 开工检查 `git status`、branch、remote、HEAD、是否存在未提交工作。不得覆盖他人文件；已有修改先辨明归属。
- 新任务从最新 `origin/main` 建分支，并把基线 SHA 填入 Issue/报告；进行中的分支通过 merge 更新主线，不重写已推送历史。

示例：在工作区无未提交变更、已核实仓库之后，TARGET 建新任务分支：

```powershell
git fetch origin
git switch -c codex/target/color-detect-v1 origin/main
```

MAIN、LATENCY 使用各自前缀。已有同名分支时先检查，不能覆盖或删除后重建。

### 5.2 Issue 是任务与协议变更的交接点

每项任务的负责人确认内容必须包括：角色、目标、基线 SHA、允许修改范围、接口版本、依赖、交付物和验收条件。AI 未取得 GitHub Issue 创建权限时可先提交等价任务说明，不能因工具缺少权限自行扩大范围。

- 队友提出主线问题时提交可复现的 Issue，附版本/信号/证据/建议，不直接修主线。
- MAIN 拟改变接口、像素排列、时钟、帧身份、缓存策略或颜色处理时，先开接口变更 Issue，明确受影响角色和迁移方式。业务参数变化也需说明是否影响颜色阈值或测量精度。
- 受影响队友在 Issue 中确认理解并给出影响分析；MAIN 确认新接口版本后，各角色在自己的分支适配。没有明确消息授权时，AI 只准备通知文字和报告，由人类发出。
- 并行工作使用已确认的接口版本；未落实的接口用显式仿真驱动，报告“硬件依赖未接入”。主线暂时缺少接口不允许伪造整机完成状态。

### 5.3 提交、推送和 PR

1. 仅显式 stage 本任务文件；禁止用 `git add .` 混入本地未跟踪参考工程、私人文件或大型构建目录。
2. 每次 push 前执行根 AGENTS 要求的状态、diff、文件范围、敏感信息、bit/构建目录检查；发现疑似凭据时停止上传，报告路径和原因，不打印敏感值。
3. 将提交推送至自己的分支。每个形成实际意义的版本同步远程；不能将协作成果只留在本地。push 失败时如实报告。
4. 创建指向 `main` 的 PR，未完成或缺验证时使用 Draft。首次说明注明功能是否已接入主线，是否生成 bit，是否真实上板。
5. 请求 `Philid14` 审查；GitHub 不允许请求同一账号自审时，在报告中注明，等待人类负责人确认，不伪造其他账号或审批。
6. 两位队友及其 AI 不直接 push `main`，不合并 PR、不启用 auto-merge，不改仓库权限或审查规则。MAIN AI 也不能把本协议视为对所有未来合并的预授权。
7. 人类负责人审查当前最新 SHA 后决定合并。审查后追加提交，原确认失效，必须重新审查。修改意见继续提交到原分支/PR，不能换 PR 绕过意见。
8. 合并采用 **Create a merge commit**，保留源码/构建引用的 commit SHA。禁止 squash/rebase 合并实验历史、force push、移动已有 tag 或删除失败版本。
9. 合并后的独立模块先记“已入库”；MAIN 另建集成分支接线、完整构建和上板。最终状态必须区分独立完成、已合并、已接入、构建通过、实板通过。

推送示例：使用与当前任务匹配的具体文件和分支名称；按步骤检查成功再执行下一项：

```powershell
git add -- features/color_target/
git diff --cached --stat
git diff --cached
# 完成敏感信息、范围和必要验证检查后：
git commit -m "feat(target): add standalone color target detector"
git push -u origin codex/target/color-detect-v1
```

### 5.4 审查约束的实际能力

本团队当前选择流程审查，不要求购买套餐，也不由 AI 自动配置保护。个人私有仓库协作者有写权限，GitHub 不会因为本文件而阻止直接推送/合并。目录所有权、MAIN 独占接线和负责人审批需要三人遵守；如果要服务器强制执行，负责人另行决定套餐、CODEOWNERS 与分支保护设置。

## 6. 版本、板卡与证据协议

- 全系统可上板版本由 MAIN 统一命名、构建、归档和签发 tag；独立模块仿真通过不生成“整机已验证”tag。
- 源码 commit、bit 归档 commit、candidate tag 和测试结果 commit 按根 AGENTS 保持可追溯关系。若分支上产生了实际实验 bit，同样完整归档并推送该分支，不能省略失败实验记录。
- 不因 PR 合并 SHA 与构建源码 SHA 不同而篡改 BUILD_INFO；merge commit 保留原源码提交，记录真实构建输入。candidate/final tag 不互相移动。
- 一套板卡用预约 Issue 记录使用者、时间、批准的版本及回滚版本，同一时段只有一个操作者。队友可按确认后的操作步骤使用归档 bit，不自行改曝光、PLL、引脚或现场试烧未知 bit。
- 上板开始记录版本/tag、bit SHA-256、板卡/摄像头、显示器、线材、供电和光照。出现异常记录触发条件并回滚批准的对照版本，禁止只写“效果不好”。
- 交付验收包括本功能正确性、复位/异常场景、视频持续吞吐、结果与帧匹配、必要资源/时序证据；整机验收包含原链路、Logo、明暗变化和长期运行。没有测量能力的溢出/帧率/延迟数据填“未测”。
